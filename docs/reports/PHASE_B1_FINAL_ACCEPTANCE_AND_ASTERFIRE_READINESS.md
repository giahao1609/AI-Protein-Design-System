## 3. Scheduler Integration Audit & API Boundary

### 3.1. Implementation Reality vs. Cloud Integration
A rigorous audit confirms:
- **`ConcurrencySafeScheduler` in `src/protein_design/core/concurrency.py` is a standalone in-process Python DAG orchestrator.**
- **It is NOT connected to the AsterFire cloud submission runner or cluster API.**
- AsterFire (`SAI-compute-NEW`) is an external managed platform agent with its own remote scheduling queue and hardware allocations.
- There is currently **no active network client, webhook, or gRPC/REST connection** in the codebase that allows local Python code to control AsterFire queue dispatch directly.

### 3.2. Integration Boundary & Contract
The actual operational boundary between the AI Protein Design System and AsterFire is file-based and schema-based:
1. **Input Artifacts (Outbound to AsterFire):**
   - Cleaned receptor PDBs and FASTA sequence specifications generated by local target prep.
2. **Output Artifacts (Inbound from AsterFire):**
   - `thresholds.json`: Produced by AsterFire node `threshold_compute` from running 20 negative control decoys per track. Ingested via `src/protein_design/validation/calibration.py`.
   - `predicted_complexes/*.cif` and `scores.csv`: Produced by AsterFire GPU nodes running ESMFold2 multimer inference.
3. **Local Scheduler Value:**
   - `ConcurrencySafeScheduler` provides serialized execution (`max_concurrency=1`), bounded exponential backoff (`delay = base * 2^(retry-1)`), and cryptographic fingerprinting (`calculate_task_fingerprint`) for local batch jobs and subprocess calls (e.g. local BindCraft/PDBFixer invocations), preventing local workstation overload.
   - It guarantees resume idempotency (`SKIPPED_CACHED`) by verifying that existing artifacts match input, configuration, and model version hashes.
   - **Crucial Boundary Finding:** We do NOT claim that local `ConcurrencySafeScheduler` prevents cloud-level concurrency conflicts on AsterFire. AsterFire concurrency throttling must be granted by the AsterFire Platform Admin at the cluster quota level.

## 5. End-to-End Score Provenance Audit

### 5.1. Provenance Classification Hierarchy
The system enforces four immutable provenance states in `src/protein_design/schemas/common.py`:
- `HEURISTIC_PROXY`: Offline mathematical or heuristic estimation (e.g., sequence-hash pseudo-metrics).
- `MODEL_PREDICTED`: Authentic forward-pass deep learning model inference (ESMFold2, AlphaFold2 multimer) on a real GPU backend.
- `EXPERIMENTAL`: Wet-lab biophysical measurement (SPR, BLI, ELISA, FACS Kd).
- `UNVERIFIED`: Placeholder, missing, or uncalibrated metric.

### 5.2. Pipeline Tracing from Prediction to Submission
1. **Prediction Layer (`esmfold_ipsae.py`):**
   - Offline simulation automatically sets `metrics["score_provenance"] = "HEURISTIC_PROXY"`, `is_model_predicted = False`, `is_experimentally_validated = False`.
   - When `require_real_model=True` and no GPU model backend is loaded, `predict()` returns `ipsae_score: None`, `score_status: "UNAVAILABLE"`, `score_provenance: "UNVERIFIED"`.
2. **Validation & Storage Layer (`MetadataStore` in SQLite):**
   - All candidates are persisted in table `candidates` with their full metrics dictionary and `scientific_status`.
   - Candidate `scientific_status` remains `GENERATED` until verified by independent evaluation.
3. **Ranking Layer (`CompetitionCampaignRunner` in `campaign.py`):**
   - Candidate sorting safely handles None scores: `key=lambda c: float(c.metrics.get("ipsae_score") or 0.0)`.
   - Candidates without valid scores or developability failure are filtered out.
4. **Export Gate (`verify_export_safety` in `safety.py` & `submission.py`):**
   - Fail-closed verification blocks any candidate produced by `dummy` generators or lacking structure coordinates.
   - Only validated 20 natural amino acid sequences within competition length bounds ([40, 100] for minibinders, [100, 150] for VHH) without prohibited purification tags (His6, Flag, Myc, Strep) can be exported into `{Target}_submission.csv`.

### 5.3. Interchain PAE & ipSAE Scientific Requirements
- **Formula:**
  $$\text{ipSAE} = \left(\frac{1.0}{1.0 + (\text{interface\_pae} / 10.0)}\right) \times \left(\frac{\text{pLDDT}}{100.0}\right) \times \text{contact\_factor}$$
- **Structural Confidence vs. Binding Affinity:** ipSAE measures predicted structural alignment confidence across the complex interface. **It is NOT an experimental dissociation constant ($K_D$) or physical free energy ($\Delta G$).** High ipSAE indicates the deep learning model has high confidence in the relative orientation of the two chains; it does not guarantee thermodynamic stability or wet-lab binding.

## 6. Calibration Terminology & Statistical Justification

### 6.1. In-Silico Calibration vs. Wet-Lab Measurements
- **In-Silico Decoy Threshold:** Derived computationally by evaluating 20 non-cognate "decoy" target-binder pairs. The noise floor is defined as $\mu_{\text{decoy}} + 2\sigma_{\text{decoy}}$ (or empirical 95th percentile).
- **Physical Meaning:** A candidate scoring above this threshold demonstrates structural interface confidence superior to random background pairing in the model. It remains a purely computational filter.

### 6.2. Statistical Justification of $N \ge 20$ Decoy Policy
1. **Variance Estimation Stability:** The sample variance of a normal distribution with $N$ samples has variance $\text{Var}(s^2) = \frac{2\sigma^4}{N-1}$. For $N < 20$, the standard error in estimating $\sigma$ exceeds 32%, creating unacceptably wide confidence intervals for the $+2\sigma$ cutoff.
2. **Tail Coverage:** With $N = 20$, degrees of freedom $df = 19$ provides adequate power to reject non-specific binders while maintaining manageable compute cost (20 forward passes per target).
3. **Near-Zero Denominator Protection:** `assess_calibration_quality()` explicitly prevents division by zero when $\text{noise\_floor} < 10^{-4}$, flagging `is_reliable = False`.
